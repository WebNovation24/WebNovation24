Authority, durable workflows and provider reconciliation.

A private multi-tenant TypeScript SaaS where a valid session, current business access and uncertain external-provider outcomes must never be treated as the same thing.

01 · Problem

Authentication can outlive business authority.

A user can hold a valid browser session after their organization membership has been suspended. Treating authentication as authorization would keep access alive too long.

Constraint

Identity is not capability

The product needed a current server-side answer to “what may this actor do now?” rather than trusting stale client or session state.

Scope decision

Build the authority foundation first

I prioritized organization membership, authorization boundaries, RLS-backed data access and operational states before widening the travel feature surface.

User/product consequence

Revocation becomes immediate

Business access follows current membership state rather than waiting for the authentication session to expire.

02 · What I built

A TypeScript system that separates session, authority and external outcomes.

The work spans product behavior and backend boundaries instead of hiding long-running travel operations behind synchronous request paths.

01

Authorization foundation

Current organization membership and server-side actor context determine business capability.

02

RLS-backed access

03 · Decisions & trade-offs

Keep authority explicit at every boundary.

The architecture was shaped around observable failure modes, not around adding abstractions for their own sake.

Authorization

Rebuild current authority from server-side state.

A valid authentication session identifies the user; current organization membership answers whether the requested business operation is still allowed.

Async operations

Move uncertain provider work out of synchronous request paths.

Leases, retries and dead-letter recovery make long-running operations explicit instead of pretending a timeout means success or failure.

Scope control

Ship the reliable foundation before the full travel surface.

Core authority, workflow state and reconciliation came first so later product modules could inherit the same operational rules.

04 · Evidence

The authorization invariant is independently reproducible.

The production repository remains private. A small public TypeScript reproduction demonstrates the current-membership rule without exposing private schemas or business data.

Current authority
export function authorizeOrganization(
  identity,
  requestedOrganizationId,
  membership,
) {
  if (!identity.sessionValid) return deny("invalid-session");

  if (!membership ||
      membership.organizationId !== requestedOrganizationId ||
      membership.userId !== identity.userId) {
    return deny("membership-missing");
  }

  if (membership.status !== "active") {
    return deny("membership-inactive");
  }

  return { kind: "allowed", organizationId: requestedOrganizationId };
}
Focused regression

The same valid session loses business access after suspension.

  • active membership → allowed
  • suspended membership → denied
  • cross-organization membership → denied
  • identity and business capability remain separate

Operational evidence beyond authorization

Durable provider work uses explicit states, bounded claiming, retries and recovery paths. Reconciliation protects newer business state from stale or out-of-order external outcomes instead of treating provider responses as automatic truth.

05 · Outcome

Business access and provider state stay explicit.

Immediate revocation

Suspending membership removes business access even when the authentication session remains valid.

Recoverable async work

Long-running operations have visible failure and recovery paths instead of disappearing behind request timeouts.

Safer reconciliation

External events are processed as evidence to reconcile, not as unconditional authority over newer product state.
