02 · Challenge

Keep authority proportional to what the system knows.

AI usage data can support cost analysis, forecasting and optimization, but product semantics become risky when the interface implies more certainty than the underlying evidence supports. A recommendation is not an executed change. An executed change is not automatically a measured outcome. A measured outcome is not, by itself, causal proof of business impact.

03 · Technical decisions

Semantics, async work and scoped proof.

Three decisions show how the product avoids claiming more than the system can establish.

01

Keep product authority proportional to evidence

Problem. A cost/optimization product can make a workflow appear more conclusive than the underlying data permits.

Decision. Model applied changes, measured outcomes and user-confirmed outcomes separately; keep observation, recommendation and runtime enforcement as distinct capabilities.

Verification. Product Truth is versioned and unit/integration test harnesses cover the documented behavior.

02

Separate background work from request handling

Problem. Provider and data-processing work can exceed the responsibilities of a synchronous web request.

Decision. Use background workflow infrastructure for asynchronous processing instead of hiding long-running work inside request paths.

Verification. Inngest is an evidenced dependency and the repository includes unit/integration test scripts.

03

Treat release evidence as scoped evidence

Problem. Tooling presence or a previous deployment can be mistaken for proof that the current candidate is valid.

Decision. Use explicit unit/integration gates and release discipline rather than relying on configuration presence alone.

Verification. Public evidence supports the existence and scope of those gates, not universal correctness.
