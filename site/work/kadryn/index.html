Case study · Kadryn

Evidence, governance and reliable SaaS workflow semantics

Kadryn is a SaaS system that observes AI usage and cost signals, derives operational insight, and keeps recommendation, decision and runtime control as distinct product concepts.

TypeScriptNext.jsReactPostgreSQLPrismaStripeInngestSentryVitest
Central challenge

How do you design a cost-governance product without allowing product language or workflow state to overstate what the system actually knows?

Constraints

Evidence boundary · Capability boundary · Integration surface · Verification scope · Private source repository.

Context

AI usage data can support cost analysis, forecasting and optimization, but product semantics become risky when the interface implies more certainty than the underlying evidence supports. A recommendation is not an executed change. An executed change is not automatically a measured outcome. A measured outcome is not, by itself, causal proof of business impact.

Public-safe explanatory model
Observe — usage and cost signals
↓ evidence supports, but does not authorize
Recommend — proposed action with context
↓ explicit decision boundary
Apply / enforce — only through the relevant control path
↓ separate measurement
Measure — outcome evidence without an automatic ROI claim

Technical decisions

Three decisions show how product semantics, asynchronous work and release evidence stay scoped.

01

Keep product authority proportional to evidence

Problem
A cost/optimization product can make a workflow appear more conclusive than the underlying data permits.
Constraint
Applied changes, measured outcomes and user-confirmed outcomes are different states, and none automatically establishes causal ROI.
Decision
Model those states separately and keep observation, recommendation and runtime enforcement as distinct capabilities.
Implementation
Kadryn’s current Product Truth defines separate semantics for observed data, recommendations, governance and enforcement paths.
Verification
The canonical Product Truth is versioned, and the repository includes unit and integration test harnesses.
02

Separate background work from request handling

Problem
Provider and data-processing work can exceed the responsibilities of a synchronous web request.
Constraint
External or long-running operations need their own execution lifecycle.
Decision
Use background workflow infrastructure for asynchronous processing.
Implementation
The application stack includes Inngest and operational data-workflow tooling.
Verification
Inngest is an evidenced dependency and unit/integration test scripts are present.
03

Treat release evidence as scoped evidence

Problem
A configuration file or previous deployment can be mistaken for proof that the current candidate is valid.
Constraint
Changes can invalidate earlier evidence, and test configuration is not a passing run.
Decision
Use explicit unit/integration gates and release discipline rather than relying on tooling presence alone.
Implementation
Kadryn exposes unit and integration test commands and repository rules that distinguish code presence from runtime/release proof.
Verification
Public evidence supports the existence and scope of those gates, not universal correctness.
Evidence / verification
Public-safe evidence includes the TypeScript/Next.js/PostgreSQL/Prisma stack, Stripe-related infrastructure, Inngest background workflows, Sentry integration, and unit/integration test harnesses. It does not support customer ROI, adoption or universal system reliability claims.
Observable outcome

Claims bounded by explicit evidence states.

The observable technical result is a SaaS architecture and product model in which operational claims are bounded by explicit evidence states, while billing, background processing and test infrastructure are part of the application stack.

What this demonstrates

Project-level capabilities supported by public evidence; no blocked first-person attribution is implied.
